## 24.1 The spin-chain Hamiltonian

Chapter 23 minimized an energy by trying many different trial states against a *fixed*
Hamiltonian. This chapter fixes the initial state instead and asks the complementary question:
how does `|ψ⟩` evolve *in time* under a Hamiltonian `H`? That question — simulating physics
directly on a quantum computer — is Feynman's original 1982 motivation for building one at all,
and no earlier chapter in this book has done it.

Time evolution is generated by the Schrödinger equation, whose solution for a time-independent
`H` is the single operator `U(t) = e^(−iHt)` (`ħ = 1` throughout). Because `H` is Hermitian,
`U(t)` is unitary — in principle a perfectly legal quantum gate. The catch is that for a sum of
non-commuting terms, `e^(−i(A+B)t) ≠ e^(−iAt)·e^(−iBt)` in general, so there's no closed-form
single gate for `U(t)` when `H` is a sum of terms that don't commute — exactly this chapter's
situation.

The target is a 2-qubit **transverse-field Ising chain**, the standard toy model for this kind
of demonstration:

```text
H = −J·Z⊗Z − h·(X⊗I + I⊗X),   J = 1.0,  h = 0.5
```

`Matrix` now has `+`, scalar `*`, and `⊗` (the same modernization Chapters 21 and 23 used), so
`H` is one expression, not an entrywise loop:

```swift
let H = (Z ⊗ Z) * (-J) + (X ⊗ I2) * (-h) + (I2 ⊗ X) * (-h)
```

Unlike Chapter 23's H₂ Hamiltonian, which needed the Jordan–Wigner transform to turn fermionic
creation/annihilation operators into Pauli strings, this is already a native spin (qubit)
model — there's no fermion-to-qubit mapping step to derive. What it does share with H₂ is the
reason it's hard: its terms don't all commute with each other. `Z⊗Z` commutes with itself, but
not with `X⊗I` or `I⊗X` — confirmed directly, not assumed, in §24.6 — and that non-commutativity
is exactly why `U(t)` can't be built as a single gate and has to be split into pieces small
enough to compile.

## 24.2 An `expm` ground truth

`Matrix` still has no matrix exponential, so one is built here, at the page level, by
scaling-and-squaring Taylor series — built only from `Matrix *` and `+`, which now exist in
Core:

```swift
func expm(_ A: Matrix, terms: Int = 20) -> Matrix {
    let n = A.rows
    var normEst = 0.0
    for i in 0..<n { for j in 0..<n { normEst = max(normEst, A[i, j].magnitude) } }
    var s = 0
    var scaled = A
    var normS = normEst
    while normS > 0.5 { scaled = scaled * 0.5; normS *= 0.5; s += 1 }
    var result = Matrix.identity(size: n)
    var term = Matrix.identity(size: n)
    for k in 1...terms {
        term = (term * scaled) * (1.0 / Double(k))
        result = result + term
    }
    for _ in 0..<s { result = result * result }
    return result
}
```

Before trusting this as ground truth for anything else, it's checked against an *exact* gate —
Core's `RXGate`, which is `exp(−iθX/2)` with no approximation:

```text
expm(-iθX/2) vs. RXGate.matrix(θ=0.7): max diff = 1.11e-16
```

Agreement to machine precision — `expm` is trustworthy.

## 24.3 ZZ(θ) as an exact gate identity

The key building block for splitting `H` into gates is `exp(−iθ·Z⊗Z/2)`, and it turns out to
have an *exact* gate-level identity, not an approximation: `cx(0,1); rz(θ,1); cx(0,1)`.

The reason is CX-conjugation. `cx(0,1)` maps a computational basis state `|q0 q1⟩` to
`|q0, q1⊕q0⟩` — it flips q1 exactly when q0 is `1`. Core's `RZGate` is exactly
`exp(−iθZ/2)`, a phase that depends on q1's own value alone. Conjugating that phase gate by
`cx(0,1)` — apply the CX, then the phase, then the CX again to undo the flip — turns "the phase
depends on q1's value" into "the phase depends on q0⊕q1's value," i.e. it turns the generator
`I⊗Z` into `Z⊗Z`. No sign correction is needed in Core's convention:

```swift
func zzViaGates(_ theta: Double) -> Matrix {
    let cx = CNOTGate.matrix(qubits: 2, control: 0, target: 1)
    let rz1 = I2 ⊗ RZGate.matrix(theta: theta)
    return cx * rz1 * cx
}
```

Checked against `expm` directly, not assumed:

```text
expm(-iθZ⊗Z/2) vs. cx;rz;cx (θ=0.7): max diff = 1.24e-16
```

Machine precision again — this is an exact identity, and it's the only piece of `H` above that
compiles into gates without any approximation at all.

## 24.4 Trotter error shrinking as 1/n

The other two terms, `X⊗I` and `I⊗X`, are just single-qubit `RXGate`s tensored up — no identity
needed there. The obstacle is combining all three: `H`'s ZZ term and X terms don't commute
(§24.6), so `exp(−iHt)` isn't `exp(−iH_ZZt)·exp(−iH_Xt)`. The **first-order Trotter (Lie–Trotter)
formula** approximates it anyway by chopping the total time `t` into `n` small steps of size
`dt = t/n`:

```swift
func trotterUnitary(_ t: Double, _ n: Int, order: Int) -> Matrix {
    let dt = t / Double(n)
    let uZZ = zzViaGates(-2 * J * dt)
    let rxQ0 = RXGate.matrix(theta: -2 * h * dt) ⊗ I2
    let rxQ1 = I2 ⊗ RXGate.matrix(theta: -2 * h * dt)
    let step: Matrix
    if order == 1 {
        step = rxQ1 * rxQ0 * uZZ
    } else {
        let uZZhalf = zzViaGates(-2 * J * (dt / 2))
        step = uZZhalf * rxQ1 * rxQ0 * uZZhalf
    }
    var result = Matrix.identity(size: 4)
    for _ in 0..<n { result = step * result }
    return result
}
```

(The `-2 * J * dt` angle comes from matching `rz(θ) = exp(−iθZ/2)` against the `−J·Z⊗Z` term's
own coefficient: `exp(−i(−J·dt)·Z⊗Z) = zzViaGates(−2·J·dt)`.) Each single step has error
`O(dt²)`; accumulated over `n = t/dt` steps, the total error is `O(dt) = O(t/n)` — shrinking as
`1/n`:

```text
1st-order Trotter error (max diff from exact), t=1:
  n=1   0.374436
  n=2   0.178803   ratio = 0.477525
  n=4   0.087851   ratio = 0.491330
  n=8   0.043722   ratio = 0.497684
  n=16   0.021835   ratio = 0.499412
  n=32   0.010914   ratio = 0.499853
```

The ratio column — each row's error divided by the previous — converges to 0.5: doubling the
step count roughly halves the error, the textbook `O(1/n)` scaling for first-order Trotter.

## 24.5 Suzuki's second-order correction: 1/n²

A small change to the step's internal order — splitting the ZZ layer into two half-strength
applications, one before and one after the X layer — cancels the leading error term and buys a
full order of convergence:

```text
step = zzViaGates(-J·dt) · [X layer] · zzViaGates(-J·dt)   (half-strength ZZ on each side)
```

(`order == 2` in `trotterUnitary` above.) Across `n` repeated steps, the boundary between one
step's trailing half-ZZ and the next step's leading half-ZZ merges into a single full-strength
ZZ application, so the sequence over `n` steps is `[half-ZZ, X, ZZ, X, ZZ, …, X, half-ZZ]` —
`n − 1` full ZZ layers plus 2 half layers, the same asymptotic gate count as first order's `n`
ZZ layers, at a much better error:

```text
2nd-order (Suzuki) Trotter error:
  n=1   0.139583
  n=2   0.029407   ratio = 0.210681
  n=4   0.007011   ratio = 0.238414
  n=8   0.001732   ratio = 0.247016
  n=16   0.000432   ratio = 0.249249
  n=32   0.000108   ratio = 0.249812
```

The ratio converges to 0.25 instead of 0.5 — `O(1/n²)`: doubling `n` roughly *quarters* the
error, for essentially the same gate budget per step as §24.4.

## 24.6 Why non-commuting terms cause the error at all

Both error tables above are symptoms; the cause is that `Z⊗Z` and `X⊗I` don't commute. Computed
directly rather than asserted:

```text
max |[Z⊗Z, X⊗I]| entry: 2.000000
```

Manifestly non-zero. As a contrast, a Hamiltonian with only *one* term has nothing to split:
dropping the field entirely (`h = 0`, `H = −J·Z⊗Z` alone), first-order Trotter at `n=1` is
*exact*:

```text
commuting-only Hamiltonian (h=0), n=1 error: 0.00e+00
```

The error doesn't come from `exp()` itself, or from the ZZ or X gates individually (both are
exact, §24.2–24.3) — it comes entirely from approximating the sum of two things that don't
commute as a product of two separate exponentials.

That error is also visible at the level of an actual observable, not just an abstract operator
norm. Starting from `|00⟩`, tracking `⟨Z₀⟩(t) = ⟨ψ(t)|Z⊗I|ψ(t)⟩` for the exact evolution against
first-order Trotter at `n=2` and `n=8`:

```text
⟨Z₀⟩(t): exact vs. Trotterized n=2, n=8
t       exact       n=2         n=8
0.500000   0.887408    0.885076    0.887264
1.000000   0.671987    0.645963    0.670495
1.500000   0.564117    0.502502    0.561433
2.000000   0.593988    0.586589    0.597826
2.500000   0.577348    0.820916    0.601325
3.000000   0.359154    0.990043    0.409120
```

At `t=1`, `n=8` (`0.670495`) tracks the exact value (`0.671987`) far more closely than `n=2`
(`0.645963`) — the observable-level error shrinks the same way the operator-level error does.
Both columns drift more at larger `t` (`n=2` is badly off by `t=2.5`–`3.0`): a **fixed** step
count `n` means the per-step size `dt = t/n` grows as the *total* simulated time `t` grows, and
since Trotter error depends on `dt` (not `n` alone), simulating further into the future needs
proportionally more steps to hold the same accuracy, not just a fixed `n`.

## Build it in the app

◐ Every gate a first-order Trotter step needs — `cx`, `rz`, `rx` — is in the palette, so a
complete `n`-step evolution is tappable, column by column; only the `expm` ground truth, the
error-vs-n sweep, and the commutator stay code-only.

One first-order step at `t=1`, `n=2` (so `dt = 0.5`): the ZZ angle is `-2·J·dt = -1.0` and the
RX angle is `-2·h·dt = -0.5`. The θ popover's slider only runs 0 to 2π, so both go in as
`2π − x`, the same negative-angle trick Chapters 20–23 used (`RZ(2π−x)` differs from `RZ(−x)`
by an overall factor `exp(−iπZ)`, which is exactly `−I` for either Z eigenvalue — a global phase
that doesn't touch any probability).

1. Clear, set **Qubits: 2**.
2. Arm **CX**, tap `q0` then `q1` in column 0 — q0 control, q1 target.
3. Arm **RZ**, tap `q1` in column 1 — drag to `θ = 5.283` (`= 2π − 1.0`).
4. Arm **CX**, tap `q0` then `q1` in column 2 (same control/target as step 2).
5. Arm **RX**, tap `q0` in column 3, then arm **RX** again and tap `q1` in the *same* column 3
   (parallel placement) — both to `θ = 5.783` (`= 2π − 0.5`).
6. Repeat columns 0–3 as columns 4–7 for the second step.

State Vector panel after all 8 columns — probabilities:

```text
|00⟩ ≈ 0.686651   |01⟩ ≈ 0.136331   |10⟩ ≈ 0.136331   |11⟩ ≈ 0.040687
```

`⟨Z₀⟩ = P(q0=0) − P(q0=1) = (0.686651+0.136331) − (0.136331+0.040687) ≈ 0.645963` — matching
§24.4/§24.6's code-computed `n=2` value exactly.

**What's still out of reach:** the `expm` ground truth, the error-vs-n sweep across six step
counts, the commutator computation, and the multi-`t` observable table are all "Run it in code"
below — `CircuitBuilder` has no way to compute a target unitary directly or run a parametric

## Try it yourself

1. Compare first-order and Suzuki second-order Trotter error at the same step count, e.g. n=8.
   <details><summary>Answer</summary>First-order: 0.043722. Second-order: 0.001732 — about 25×
   smaller, consistent with §24.4/§24.5's `O(1/n)` vs. `O(1/n²)` scaling at this `n`, `J`, `h`,
   and `t`.</details>
2. Why is the ZZ-only Hamiltonian (`h = 0`) exact at `n=1`, with no splitting error at all?
   <details><summary>Answer</summary>Trotter error comes from approximating
   `exp(−i(A+B)t)` as `exp(−iAt)·exp(−iBt)` when `A` and `B` don't commute. With only one term,
   there's nothing to split — `exp(−iH_ZZt)` is applied directly via the exact `zzViaGates`
   identity from §24.3, with no product-formula approximation anywhere in the pipeline. Verified:
   0.00e+00, not just very small.</details>
3. Reverse the order of the two layers in a first-order step — X-layer first, then ZZ, instead
   of ZZ then X. Does the error change?
   <details><summary>Answer</summary>No: run at n=1,2,4,8, the reversed-order error matches the
   original order's error to floating-point precision (diff ~1e-17) at every n. The two step
   matrices are similar (`step_reversed = R⁻¹ · step_original · R` for `R` the commuting pair of
   single-qubit X-rotations, since `Z'R` and `RZ'` are always conjugate via `R` for any two
   matrices `R`, `Z'`), which guarantees they share eigenvalues — and empirically, at least for
   this Hamiltonian and this error metric, that's enough to make the two error curves
   indistinguishable at every step count tried.</details>
4. Extend to a 3-qubit chain, `H = −J·(Z₀Z₁ + Z₁Z₂) − h·(X₀+X₁+X₂)`. Do the two ZZ terms commute
   with *each other*? Does the first-order error still shrink with n?
   <details><summary>Answer</summary>Yes and yes. `[Z₀Z₁, Z₁Z₂]` computed directly: max entry
   magnitude 0.0 — any two Pauli-Z strings always commute with each other, overlapping qubit or
   not, since `Z` is diagonal. So the two ZZ terms can go in either order (or the same layer)
   within a Trotter step with no extra splitting error between them. But the field terms still
   don't commute with the ZZ terms, so the overall error still shrinks with n much like the
   2-qubit case: n=1 → 0.444165, n=2 → 0.181926, n=4 → 0.087454, n=8 → 0.042941,
   n=16 → 0.021285 — still roughly halving, `O(1/n)`, driven entirely by the ZZ/field
   non-commutativity, not by the two ZZ terms themselves.</details>
